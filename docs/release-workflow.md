# Release workflow

How to record a change and how to make a release. The design behind it - the data model, the rules, the generated
files - is [release-architecture.md](release-architecture.md).

Everything goes through one command, `python scripts/release.py` (in a checkout: `uv run python scripts/release.py`).
Every command runs without questions when given its options (for agents and CI); `change` and `prepare` ask for what
is missing when run at a terminal. Exit codes: 0 ok, 1 problems found, 2 usage error.

**Never edit `CHANGELOG.md` or `backend/autoapply/releases.json` by hand**: they are generated, and CI fails when they
are not what the data gives.

## 1. Does the change need a fragment?

A fragment is for what a **user notices**: a new capability, a behaviour or a page that works differently, a bug they
could hit, something removed or deprecated, a security fix, a new package or a change to installing or updating.

No fragment for what users do not see: refactoring, tests, CI, documentation for contributors, internal renames, a
change to a pending feature that has its own fragment already (update that fragment instead). Say so in the pull
request: tick *No user-visible change* (or write `no-changelog` in the description). CI only reminds, it does not
block: a pull request that changes `backend/autoapply` or `frontend/src` without a fragment gets a warning.

One fragment per change a user would name separately. A pull request may add several; a big feature with many small
parts is usually one fragment with the parts in its details.

## 2. Write a fragment

```bash
python scripts/release.py change --type fixed --scope calendar \
  --summary-en "Quiet hours follow your time zone, not the computer's clock" \
  --summary-zh "免打扰时段按你的时区计算，而不是电脑的时钟" \
  --details "With the program running on a server in another time zone, quiet hours were someone else's night." \
  --pr 131
# prints changes/fragments/2026-11-24-quiet-hours-follow-time-a3f9.md
```

Options: `--type`, `--scope`, `--summary-en` (required), `--summary-zh`, `--summary-fr`, `--details TEXT` or
`--details-file PATH`, `--highlight`, `--bump minor|major`, `--pr N` (repeatable), `--slug words-for-the-name`. Run
it with no options at a terminal to be asked. The file name is made for you (date, slug, 4 random hex digits): two
people or agents writing at the same moment get two files. After that, edit the file freely while it is pending -
the details especially.

**Type** - what kind of change: `added` (a new capability), `changed` (something works or looks differently),
`deprecated` (still works, will go), `removed` (gone), `fixed` (a bug), `security` (a vulnerability fixed or a
protection added).

**Scope** - which part of the product (independent of the type; the list lives in
`changes/schema/fragment.schema.json`):

| Scope | | Scope | |
|---|---|---|---|
| `postings` | finding, sources, scoring, the postings page | `analytics` | the analysis page |
| `applications` | application records, approval, the applications page | `ai` | AI services, models, failover, budgets |
| `agent` | the application agent and its browser work, playbooks | `settings` | settings not covered by another scope |
| `mail` | reading mailboxes, matching mail, sending mail | `updates` | looking for, preparing and switching versions |
| `calendar` | calendar, reminders, the calendar feed | `ui` | the interface as a whole: layout, shared components, themes |
| `notifications` | Telegram, Discord, notifications, quiet hours, the chat assistant | `i18n` | languages, translations, wording |
| `profile` | the applicant's profile and what the program knows | `packages` | installers, the zip, the container image |
| `files` | the material library, documents, cover letters | `server` | the server, the API, access and login, running on a server |
| `accounts` | site accounts, credentials, sessions, sign-in providers | `release` | the release process and its notes |

**Summary** - one line a user understands, at most 120 characters, in English: what they notice, not what the code
does ("Quiet hours follow your time zone", not "Use calendar.tz in quiet.py"). No Markdown blocks, no bold (it is
shown bold), plain inline code is fine. A summary stands alone in the app's collapsed view, so it is not a fragment
of the details.

**Translations** - `zh` (Simplified Chinese) and `fr` are optional; the app shows English, marked as such, where one is
missing. Write them when you can, in the terms of `docs/ux-writing-glossary.md`; a highlight should have `zh`
(`validate --strict` requires it). Translations are written and reviewed with the change, never generated by the
program at run time. The details stay in English (the full notes are English).

**Highlight** - one of the release's main changes, shown first when a release is opened (at most 6 per release; give
a highlight details).

**Bump** - only when the change needs more than the default patch number: `minor` or `major` (for instance a change
that breaks how an existing installation or its data works). Type and bump are separate: an `added` is still a patch
unless it says otherwise.

**Details** - Markdown after the front matter: what a user notices, as long as needed; lists, links (http(s) or
relative), code. No headings of level 1-3. They are the item's text in CHANGELOG.md and the full release notes.

## 3. Check

```bash
python scripts/release.py validate            # every fragment and manifest, the versions; problems with file and line
python scripts/release.py validate --strict   # also: highlights need summary.zh and details
python scripts/release.py status              # what is pending by type, the next version, the releases and their tags
```

## 4. Prepare a release

On a branch from an up-to-date `master`:

```bash
python scripts/release.py prepare --dry-run                       # what would be written; writes nothing
python scripts/release.py prepare --title-en "A calendar feed" --title-zh "日历订阅" --title-fr "Un flux de calendrier" \
  --intro-file intro.md --known-limit "The feed is read-only."
```

`prepare` takes every pending fragment and

- writes `changes/releases/<version>.json` (the fragments by type, highlights first, with their hashes);
- sets the version in `pyproject.toml`, `frontend/package.json`, `frontend/package-lock.json` and `uv.lock` (exactly
  those fields);
- regenerates `CHANGELOG.md` and `backend/autoapply/releases.json`, then runs `validate --release <version>`.

The version is suggested (`status` shows it and why): the current one plus a patch, or the largest `bump` a pending
fragment declares. `--version X` chooses another; it is refused when it goes back, exists already, or is smaller than
a declared bump (`--force-bump "<reason>"` to do it anyway, said in the output). `--date` defaults to today. A
pre-release is `--version 2.1.0-rc.1`; the next `prepare` suggests `2.1.0`.

Review the diff, edit the manifest's order or the titles if needed (before the tag, the candidate may change: run
`generate` after an edit), and open a pull request "Release X" with these files. CI checks it like any other.

## 5. Generate

```bash
python scripts/release.py generate            # rewrite CHANGELOG.md and backend/autoapply/releases.json
python scripts/release.py generate --check    # exit 1 and name the file when one is out of date
```

Only needed after editing a manifest or correcting a fragment by hand; `prepare` and `correct` run it themselves.
Pending fragments never change the generated files, so merging them never conflicts.

## 6. Notes

```bash
python scripts/release.py notes 2.0.3         # the GitHub release notes: the release's CHANGELOG.md section
```

## 7. Publish (the owner only)

After the "Release X" pull request is merged:

```bash
python scripts/release.py publish 2.0.3       # dry run: checks everything, prints the two commands
python scripts/release.py publish 2.0.3 --yes # runs them after you type the version
```

The dry run checks: on `master`, a clean working tree, up to date with `origin`, the manifest exists, every copy of
the version is X, `validate --release X` and `generate --check` pass, and no tag `vX` here or on `origin` (it fetches
`origin master` first; `--no-fetch` skips that). It prints `git tag -a vX -m "AutoApply X"` and `git push origin vX`,
and exits 1 when a check failed. Pushing the tag starts `.github/workflows/release.yml`:
it checks the tag and the release data again, runs the tests, builds and installs every package, publishes the GitHub
release with `release.py notes X` and the downloads table, then the container image.

An agent never creates a tag, pushes one or runs `publish --yes`: the owner does, and says so explicitly.

If the workflow fails, nothing is marked published (that is the tag's existence on a successful run): fix the cause,
delete the failed tag (`git push origin :refs/tags/vX`, `git tag -d vX`) and publish again, or prepare the next
version.

## 8. Change released text

A released fragment cannot change silently (`validate` compares it with the hash in its manifest). If its text is
wrong - a fact, a typo that matters, a missing translation - edit the fragment, then:

```bash
python scripts/release.py correct 2.0.2 2026-11-22-calendar-reminders-1a2b --reason "Added the Chinese summary"
```

The correction (date, reason, new hash) is kept in the manifest and the generated files are rewritten. A released
fragment is never deleted or renamed.

## History

Fragments began with 2.0.3. The releases before (1.0.0 - 1.0.4, 2.0.0, 2.0.2; 2.0.1 was folded into 2.0.2) were
migrated into fragments and manifests from the hand-written changelog, which is kept unchanged as
`changes/legacy/CHANGELOG-2.0.2.md` (evidence only; nothing reads it).

## Troubleshooting

| Message | What to do |
|---|---|
| `YAML: mapping values are not allowed here` on a summary line | The text has `: ` in it - put it in double quotes (`release.py change` does). |
| `found date (quote it)` | An unquoted value that YAML reads as a date: quote it. |
| `the key 'x' is given twice` | Remove one of them. |
| `is not the file name` | `id` and the file name must be equal; do not rename a fragment by hand - write a new one with `change`. |
| `"x" is not one of: ...` (scope) | Use a scope from the list; a new scope is added to `fragment.schema.json` in its own pull request. |
| `changed after its release in X` | A released fragment was edited. Undo it, or record it with `release.py correct X <id> --reason "..."`. |
| `... is 2.0.2, but pyproject.toml says 2.0.3` | The version was changed by hand somewhere: only `prepare` changes it. Put the copies back in step. |
| `generate --check`: `CHANGELOG.md differs` | Someone edited a generated file, or a manifest changed: run `release.py generate` and commit the result. |
| `X is not a minor release after Y` | A pending fragment declares `bump: minor`: use the suggested version, or `--force-bump "<reason>"`. |
| `fragment(s) are not in any release` (warning, `--release`) | Fragments were merged after `prepare`: the package would show them as not released. Either let them wait for the next release, or - before the tag exists - delete the candidate's manifest and run `prepare --version X ...` again in a new pull request. |
| `PyYAML is needed` | Run through `uv run`, or `pip install pyyaml`. |
| CI warns "No change fragment" | Add one with `release.py change`, or tick *No user-visible change* in the description. |
